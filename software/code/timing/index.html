    Le timing non bloquant¶

    Le problème à résoudre¶

    La manière naïve d'attendre dans un programme embarqué est d'appeler une fonction de pause :

    faire_action()
attendre(200ms)     ← le CPU s'arrête ici pendant 200ms
faire_suite()

    Pendant ces 200ms, tout s'arrête : les boutons ne sont plus lus, l'écran ne se met plus à jour, le son est coupé. Sur un système avec un seul jeu simple, ça passe. Sur une console avec 10 jeux et des composants qui doivent tous fonctionner en même temps, c'est rédhibitoire.

    Mais il y avait une issue pour éviter cela.

    La solution : mesurer plutôt qu'attendre¶

    Au lieu de bloquer le CPU, on mémorise l'heure à laquelle la dernière action a eu lieu, et on vérifie à chaque cycle si le délai est écoulé.

    ❌ Approche bloquante          ✅ Approche non-bloquante
───────────────────────        ──────────────────────────────
1. Faire l'action              1. Mémoriser l'horodatage
2. attendre(200ms)             2. Continuer la boucle normalement
   └─ CPU bloqué               3. Cycle suivant : vérifier si délai écoulé
   └─ boutons sourds           4. Si oui → faire l'action, mémoriser l'heure
   └─ écran figé               5. Si non → ne rien faire, revenir au cycle
3. Reprendre                   └─ boutons réactifs · écran fluide · audio actif

    Une belle analogie : un serveur au restaurant ne reste pas planté devant le four à regarder cuire chaque plat. Il regarde l'horloge, sert d'autres tables, revient vérifier. Il mesure le temps au lieu d'attendre.

    Algorithme — Timer non-bloquant¶

     Variable persistante (conservée entre les cycles)
dernière_action ← 0

mettreÀJour() :
  maintenant ← temps_actuel_ms()

  si (maintenant - dernière_action) < intervalle :
    retour                      ← trop tôt, on sort immédiatement

  dernière_action ← maintenant  ← mémoriser pour le prochain déclenchement

  logique_du_jeu()              ← maintenant on exécute

    Ce qui se passe réellement : la boucle principale continue à tourner 60 fois par seconde. À chaque passage dans mettreÀJour(), on vérifie si l'intervalle est écoulé. Si non, on sort en une microseconde. Le CPU est libre pour tout le reste.

    Chaque composant a son propre timer¶

    C'est le point le plus important : plusieurs composants peuvent avoir des rythmes totalement différents dans la même boucle, sans s'interférer.

    Boucle principale (tourne en permanence)
  │
  ├── lireEntrées()              ← chaque cycle (~1ms)
  │
  ├── serpent.mettreÀJour()
  │     └── si (maintenant - lastMove) < 150ms → retour
  │         sinon → déplacer le serpent          [150ms]
  │
  ├── envahisseurs.mettreÀJour()
  │     └── si (maintenant - lastMove) < 400ms → retour
  │         sinon → déplacer la formation        [400ms, décroissant]
  │
  └── balle_pong.mettreÀJour()
        └── si (maintenant - lastUpdate) < 16ms → retour
            sinon → physique de la balle         [16ms ≈ 60 fps]

    Chacun évolue à son propre rythme. Aucun ne bloque les autres.

    Le timer et les entrées : l'interaction correcte¶

    Le timer non-bloquant ne s'applique qu'à la logique de jeu (physique, déplacement automatique). Les entrées, elles, sont lues à chaque cycle sans condition, sinon on risque de rater un appui.

    boucle principale :
  lireEntrées()                    ← TOUJOURS, sans condition

  si (maintenant - lastUpdate) < intervalle : retour   ← le timer
  lastUpdate ← maintenant

  traiter_entrees_et_logique()     ← seulement quand le timer sonne

    Variante : le timer avec debounce¶

    Pour la navigation dans le menu, on veut à la fois la réactivité du front montant ET un délai minimum entre deux déplacements (pour éviter de défiler trop vite si le bouton est maintenu).

    si bouton_bas.pressé ET (maintenant - dernière_navigation > 200ms) :
  curseur ← curseur + 1
  dernière_navigation ← maintenant

    Ce n'est pas du timing de jeu — c'est du debounce de navigation. Le délai de 200ms est intentionnel et perceptible par l'utilisateur.

    À retenir¶

    • Ne jamais utiliser de pause bloquante dans la boucle principale d'un jeu.
    • Chaque composant qui a un rythme propre possède sa variable dernière_action.
    • Les entrées sont lues sans condition à chaque cycle.
    • La formule (maintenant - dernière_action) >= intervalle est universelle : elle fonctionne dans n'importe quel langage.
